Grow the Harness, Not the Context: From Strategy-Free Scaffolds to Reusable Specialist Agents

提出 Growing Harness：从一个「无策略脚手架」出发（只暴露模型和工具接口、不含任何任务控制逻辑），用失败轨迹把反复出现的控制决策从模型上下文迁移到可执行代码里。做法是用函数级执行 trace 把失败定位到有界代码面、批量联合修复、并用 held-out 的 success-first 门禁回滚伤害既有能力的改动。在 BrowseComp-Plus 和 WebArena-Verified、4B 到 120B 三种部署模型上，六个设置中五个取得最高平均成功率，相对 Tool-Calling agent 减少 76.0–91.8% 的 LLM 调用和 74.4–98.6% 的推理成本；WebArena-Verified 上 4B 模型仍保持 44.7% 成功率而 Tool-Calling 跌到 6.7%。

为什么值得读：正面回答「控制逻辑该放在上下文里还是 harness 代码里」，同时给出成本与小模型可用性的硬数字。

局限：harness 的成长过程本身依赖训练任务分布，跨 benchmark 的可迁移性未充分验证。

→ https://arxiv.org/abs/2609.26760

CliffCompaction: Cost-Efficient Compaction for Long-Horizon Coding Agents

CliffCompaction 是面向长时程 coding agent 的自动上下文压缩方法，核心原则是只截断/丢弃、绝不改写或复述原文，且永不压缩已压缩的内容（每次压缩只作用于原始内容，旧压缩结果直接丢弃）以避免上下文漂移累积。在有界上下文下，成本最多降低 50% 而 Terminal-Bench 性能持平或更好，并让 test-time scaling 的性价比明显改善（不到两次全上下文运行的成本换来 10+ 个百分点）。在百万 token 级的 KernelBench 连续会话上，200 步得到 2.23× CUDA kernel 加速、400 步 3.58×，超过专门的搜索算法和训练过的 agent。

为什么值得读：上下文管理与 token 预算的直接可用方案，且给出了 scaffold 无关的 API-proxy 实现，可直接接 Claude Code/Codex。

局限：论文中的模型版本号与基线标注异常（Opus 4.7、GPT-5.3 等），数字需要自行核对来源。

→ https://arxiv.org/abs/2609.26779

FIRE: Failure-Informed Runtime Engineering for Reliable Language-Model Agents

FIRE 研究「runtime policy」：在 harness 层、针对历史上导致失败的状态注入定向自然语言指令或动作禁令，不改权重也不改用户 prompt。在完整 87 任务的 Terminal-Bench 2.1 上每任务两次尝试，三档 GPT 模型的重复成功率（pass^2）全部提升，最强一档 64.4% → 73.6%，而 best-of-two 只涨 1.2 分、pass^2 涨 9.2 分，说明 policy 主要把「能做到」转化成「稳定做到」。五臂随机对照进一步排除了安慰剂效应：真实 policy 61%，无 policy 39%，时间匹配的假 policy 36%，泛化的「再验证/再考虑」提示 39–43%。

为什么值得读：把「可靠性」和「能力」分开度量（pass^2 vs pass@k），并给出一个不动模型、只动 harness 的工程层杠杆，附带干净的对照实验设计。

局限：policy 是针对已观察到的失败状态人工/半自动构造的，未验证在未见任务族上的自动生成与泛化。

→ https://arxiv.org/abs/2609.26048

Where Does Exactly-Once Live? Model, Harness, and Tool-Contract Effects on Duplicate Side Effects in LLM Agents

LIMBO 用一个含六个服务、十二种故障注入（延迟提交、重投递、部分批次等）的确定性沙盒，追问 agent 的「恰好一次」写操作语义应该由模型、harness 还是工具契约来保证。跨 9 个模型、3 个生产 harness、2 种契约变体共 25,930 个 episode：当可以立刻读回确认时模型是决定因素（前沿模型重复写仅 0.5%，模型解释了 53% 的可解释方差）；当无法确认时（请求仍在途或传输重复投递），同样的前沿模型重复率飙到 56% 和 74%，此时契约解释了 81% 的方差，而在每次写上提供 idempotency key 可把重复率从 28% 降到 4%。论文还证明了在无在途时间上界时，纯验证策略不可能保证 exactly-once。

为什么值得读：把「工具调用可靠性该在哪一层解决」量化成可归因的方差分解，对设计 agent 工具契约有直接结论；harness 几乎不影响这一结果的发现也很有信息量。

局限：结论基于合成沙盒的故障注入，真实生产 API 的故障分布与在途延迟尾部可能不同。

→ https://arxiv.org/abs/2609.29095

RRSI: Regularized Recursive Self-Improvement of Agent Harnesses

RRSI 针对「agent harness 递归自改进会过拟合训练任务」的问题，在候选提议与选择两端加正则：提议器用随时间退火的编辑预算限制单次改动捆绑量并鼓励未探索方向，选择器配 critic（筛掉 benchmark 专用改动）和 pruner（剔除过小、过贵或已失效的改动）。跨 coding、agentic workspace、工程设计共八个 benchmark，在演化所用的 split 上最多提升 14.1 分，在五个 OOD benchmark 上最多提升 4.7 分，同时最终 harness 的 policy token 消耗减少 30%。

为什么值得读：harness 自动演化目前最大的坑就是 in-distribution 涨点、OOD 归零，这篇明确把它当作核心问题处理并给出可复现的正则设计与代码。

局限：OOD 增益（≤4.7 分）远小于 ID 增益，说明过拟合只是被缓解而非解决。

→ https://arxiv.org/abs/2609.24972

Just-in-Time Memory: Learning to Curate Task-Adaptive Memory for LLM Agents

指出现有 agent 记忆系统几乎都在「写入时」策展（把轨迹蒸馏成反思/技能/工作流），这迫使系统在未知未来查询前就决定丢弃什么，且写入时策展的训练存在长时程信用分配难题。JitMem 反其道而行：保留原始轨迹，推迟到读取时、已知当前任务后再由 curator 合成紧凑的任务自适应载荷，因而可直接用当次任务成功率训练 curator。在 ALFWorld / WebShop / τ²-bench 上分别比最强基线高 16.2、16.3、3.9 个成功率百分点；即使 curator 未经训练也已能持平或超过这些写入时基线，说明增益主要来自读取时自适应这一机制本身。

为什么值得读：对 agent 记忆/上下文管理的一个结构性重新划分（写入时 vs 读取时），且用消融把增益归因到机制而非训练。

局限：保留原始轨迹意味着存储与检索规模随任务数增长，论文未讨论长期运行下的检索成本与 token 开销。

→ https://arxiv.org/abs/2609.27334
