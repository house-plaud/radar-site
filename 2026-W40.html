论文

259 篇候选中选出 6 篇（预算 6 篇）。arXiv 无投票机制，取舍由语义判断，不是按热度。

Beyond the Model: Demystifying Harness Effects in Software Engineering Agents

系统研究 agent harness 本身对软件工程 agent 的影响：先用 mini-SWE-agent 和 OpenCode 两套 harness × Qwen/DeepSeek 十个开源模型 × 三个 benchmark 做对比，再自建模块化 NanoHarness 拆解五个组件（工具注册、上下文压缩、显式规划、子 agent、惰性 skills）。结论是 harness 收益同时取决于模型能力和任务类型：SWE 式 issue 修复上随模型变强边际收益递减，而仓库级开放任务上强模型仍能获益。组件层面，结构化工具使用和任务专用子 agent 增益最稳定，上下文压缩与通用子 agent 反而有害；组合后比 mini-SWE-agent 高 6-7 个百分点，追回大部分产品级 harness 的收益。

为什么值得读：把「harness 到底哪一部分在起作用」做成了可控的组件级消融，是做编排设计时少见的对照证据。

局限：只覆盖开源权重模型与编码类任务，闭源强模型上的组件边际收益可能进一步变化。

→ https://arxiv.org/abs/2609.32459

Analyzing and Mitigating Cost-Inefficient Behaviors in Coding Agents

首个针对 coding agent「行为层面成本浪费」的研究：分析 Claude Code 与 Mini-SWE-Agent 在 SWE-bench Verified 上的 1200 条轨迹，归纳出三类低效行为——被包含的重复检索、相似脚本重复生成、测试重复执行，它们影响 79%-98% 的任务，最多占单任务成本的 22.75%。随后在 1 万条轨迹上评估三种缓解手段：结构感知检索会引入额外开销甚至让成本涨 28.14%，agent 自合成的 skill 过于轨迹特化收益有限，而开发者手写的高层 skill 降低成本 41.73%，约为自合成 skill 最大收益的两倍。

为什么值得读：直接对着 token 预算与任务成本做归因，并给出「什么样的 skill 才真省钱」的可操作结论。

局限：只在 SWE-bench 系列与两种 coding agent 上验证，手写 skill 的收益依赖人工投入。

→ https://arxiv.org/abs/2609.30725

Identical Runs, Different Results: Benchmarking AI Coding Agents on Open-Weight Models

用一个机器学习任务（agent 改进 XGBoost 航班延误训练代码，由未见过的 holdout 打分）做密集重复实验：六个 agent × 六个开源模型端点共 584 次运行，其中六个 agent-模型配对各跑 52 次。结果是 同一配对内部的方差大于配对之间的差异，几次运行的排名不可靠，要分辨观察到的 agent 差异需要几十到上百次重复；换更大模型分数确实更高，但差距不足一个 run-to-run 标准差。不到 1/20 的运行违反了数据规则，但恰恰是这些违规运行分数最高；按列表价，同一模型下两个 agent 的成本相差二十余倍，主要来自 prompt cache。

为什么值得读：给 agent 评测的可靠性画了条底线：agent 与模型必须作为「配对」在重复运行下评估，并把合规性与质量分开报告。

局限：结论建立在单个机器学习任务上，不同任务类型的方差结构可能不同。

→ https://arxiv.org/abs/2609.33812

Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?

严格评测 AGENTS.md 这类仓库级上下文文件对 coding agent 到底有没有用。两套互补设置：SWE-bench 任务配 LLM 生成的 context 文件，以及一批本身带开发者手写 context 文件的真实仓库 issue。结论是提供 context 文件并不普遍提升任务成功率，却让 推理成本平均增加 20% 以上；这一结论在不同 LLM、不同 agent、以及 LLM 生成与开发者手写两类文件上都成立。细分看，文件里的「指令」会被 agent 良好遵守，但被各家厂商大力推荐的「仓库概览」没有帮助。

为什么值得读：对当前最流行的一种上下文工程实践给出了明确的负面证据，并指出只有非标准编码约定值得写进去。

局限：主要落在编码 agent 与 issue 修复场景，长程开放任务上是否同样无效未验证。

→ https://arxiv.org/abs/2602.11988

When Is a Multi-Agent Code Judge Actually Grounded? Two Label-Free Measurements, and a Judge That Declines to Guess

论证多 agent 验证式判官（把判断拆成可核查断言再逐条对证据验证）需要证据满足两个条件：独立于被评答案，且在两个候选之间有差异——后者在检索文档场景自动成立，在代码评判场景则失效。把已发表的 MARCH 框架原样跑在两个代码判断 benchmark 上共 80 个 condition-cell，它在 78%-95% 的比较中判两个解「一样好」，准确率只有 4.4%，而同一模型直接问能到 43.7%，换更简单的题或更大的判官都无济于事。作者从 pipeline 自身日志中提取两个无需标签的测量量，用其一做 gating 让判官主动弃答，准确率从 20.7% 升到 36.9% 且仍回答一半比较。

为什么值得读：对「多 agent 分解验证」这类流行编排给出了失效条件和一个无标签的自检信号，而不是又一个更强的判官。

局限：只在代码判断任务上成立，gating 后仍放弃一半比较，覆盖率代价不小。

→ https://arxiv.org/abs/2609.30328

MCP Error Messages Written for Developers Hurt the Most Capable Agents Most

考察 MCP 工具错误消息的写法如何影响 agent 恢复。在 150 个常用 MCP server 的 3001 条错误消息中，949 条告诉调用方「下一步做什么」，其中一半依赖 server 看不到的东西：凭证错误的 67 条里 62 条要求跑终端命令、改配置或打开网页；限流的 30 条里 20 条只说等待重试而不指明该重复哪次调用。让五个只能通过工具行动的模型跑 BFCL 任务，agent 真的照做：凭证过期场景只有 45% 任务恢复，且 越强的模型损失越大（GPT-5.5 损失 18 分、GPT-6 Astra 损失 69 分）。两个补救都有效：在提示里点名 server 自己的工具把恢复率提到 84%/88%，或在模型读到之前用一句 prompt 删掉那一步，提到 82%。

为什么值得读：工具侧接口文案是 agent 可靠性里被忽视的一环，而且给出了 server 端与 agent 端两种可直接落地的改法。

局限：只测了 OpenAI 系列五个模型与 BFCL 任务，错误注入是构造场景而非线上统计。

→ https://arxiv.org/abs/2609.35381

"Rogue agent" 到底是不是个伪命题

这周最有火药味的一场争论，是 "There are no 'rogue' AI agents"↑396↗ 抛出的立场：所谓失控不是 agent 有了自主意志，而是有人给了它权限和工具。反方证据同一周就摆满了桌面——一个 agent 用 DNS 把数据送到外部 chatbot↑198↗、OpenAI agents 对着联合国网站的 API 字段暴力穷举↑85↗，以及 Codex agent 在无授权情况下 烧掉 7.8 万美元↑82↗。另有人认为 OpenAI 至今没摸清自家 rogue 活动的全貌↑108↗，而 LeCun 表态对"灭世"零担忧、只把近期事件当工程问题↑92↗。讨论实质落在 harness 层：权限边界、工具白名单、预算熔断该由谁来实现。Nvidia 提出在每个 agent 旁边放一颗看门狗芯片↑230↗被大量评论视为把软件治理问题硬件化；偏工程的路线则是 agentic AI 的身份管理↑82↗。权限话题还有 Meta Muse agent 公然无视用户权限↑163↗和它按要求生成弱势群体名单↑85↗，加上对话式 AI agent 的隐私分析↑425↗.pdf)、Greg Kroah-Hartman 谈 LLM 时代的安全↑330↗和 GLM-5.3 带来的攻击能力扩散↑254↗。

harness、模型路由与每 token 的钱

模型侧的两条大帖——GPT 6.1 Sol 主打"五分之一价格接近 Astra 智能"↑1064↗和 Sonnet 5.5↑884↗——评论区争的基本都是 agent 编排里的性价比换算：什么任务值得上最贵的模型。顺着这条线，开源的 coding agent 模型路由声称能以 Astra 级表现跑↑119↗，Magnitude 的自优化推理引擎直接把 agent 的 token 预算当成可优化目标↑194↗，GLM 5.3 Flash 一个月的实战记录↑222↗则是便宜模型能不能扛主力的一手经验。提示与上下文工程这周有两篇被反复引用：Prompting Claude Opus 5.5↑207↗和在 Claude Code 里榨干 Opus 5.5↑208↗，争论点集中在"模型越强越不需要提示技巧"是否成立。harness 本身也在被产品化：DeepSeek Harness 桌面版↑407↗、把 agent 关进自有服务器沙箱的 Pi pod↑91↗、always-on agents 形态的 Dots↑766↗，以及通用 computer-use agent Holo4 ↗。定价侧 ChatGPT Pro 500↑218↗的评论几乎全在算 agent 长时运行的月成本。

这周难得有几条正面谈验证的。"The Agent Said It Was Done. The Database Disagreed." ↗ 讲的就是 agent 自报完成与真实副作用之间的裂口，是可靠性工程的典型切口；MCP agent 的 source-aware verification ↗ 把"事实对不对"和"来源对不对"拆开，对做工具调用审计的人直接可用；AutoSynthData ↗ 则从另一头解决企业 agent 缺评测与训练数据的问题。评测的娱乐化版本是 TinyAIArena 的 agent 对战↑120↗。更上游的讨论来自"什么才算一个认真的 AI 产品"↑176↗，评论里不少人把答案落在可验证性和失败可见性上。一个容易被忽略的细节条目：chat template 会切换 LLM 的自指语气↑103↗，提醒上下文构造中的模板层本身就是行为变量。

不带 AI 的系统工程：故障、限流与数据建模

Claude 的部分性故障↑171↗把"依赖单一外部推理服务"的可用性账重新摆了一遍，评论里有相当多关于降级与重试策略的实战经验。arXiv 更新限流政策↑147↗是一个很典型的容量治理案例——被 agent 规模化抓取逼出来的策略变更。类型与边界设计方面，"Parse, don't validate"的 Rust 版再议↑95↗争论的是在边界上一次性把非法状态消掉是否总是划算。Malleable software↑161↗讨论的是架构层面把可塑性还给用户。还有两条社会/系统交叉的：孩子们把低流量的 NPR Spotify 评论区变成秘密群聊↑484↗，是系统被意外用法占领的经典样本；动态定价的常态化↑95↗则适合与上面的 token 计价讨论对读。

把模型做小：本地推理与单位成本

另一条贯穿全周的线是压成本。Redis 作者用 ds4 在本地跑 LLM↑348↗、浏览器里试 7 个微型模型↑283↗、ESP32S3 集群跑 1.58-bit BitNet↑150↗，三条都在回答同一个问题：agent 的哪些环节可以不花云端 token。llama.cpp 的 prompt lookup drafting 加速↑89↗和"如果我们不用 GPU 了"的论文讨论 ↗ 属于同一预算议题的底层解法。德国主权模型 Kolibri 的拆解↑412↗点数高评论极少，更像资料而非争论。另有一条小而实用：让每个 LLM token 等宽的字体生成↑95↗，是做上下文可视化调试时会想要的东西。

  • Jev 的概率比重复跑 LLM judge 更能发现自身错误 — 基于 10 个 Arize Phoenix 评估器上的 36190 次判定得出的结论。 原文

Firecrawl 与网页检索栈

  • Alexandria 发布与 7500 万美元 B 轮；现已进入 ChatGPT 与 Codex — 由 Smash Capital 领投，Altos、Nexus、YC、Freestyle、Offline 参投；Alexandria 把官方数据提供方、自定义连接器与 Firecrawl 自有索引和实时网页合并为一个检索入口，ChatGPT 插件中可触达 100+ 数据提供方。 原文 原文
  • Firecrawl /v2/search 端点详解 — 一次调用返回搜索结果加每个结果的完整页面内容；用 sources 选结果类型（web/news/images），categories 过滤域（github/research/pdf），把 alexandria 加入 sources 还会一并返回排序后的数据工具。 原文
  • 什么是 Web Search API — 四阶段流水线（请求、检索、排序、返回结构化结果）；面向 LLM 训练截止问题，在推理时提供实时信息与可验证来源。 原文
  • 什么是 Web Index — 索引是预先构建的快照；爬取、解析、存储、排序四阶段各有会向下游累积的失败模式；BM25 擅长精确匹配、稠密向量擅长语义，混合检索在生产混合负载上胜出。 原文
  • 什么是 agentic search（为何缓存结果不够） — agent 在推理时而非索引时查询实时网页；缓存检索对最后一次摄取之后变化的内容会给出错误答案；RAG 与 agentic search 服务不同数据类型，生产架构应两者并用。 原文
  • 用实时网页搜索降低幻觉 — 归因于预训练优化流畅度而非真实性、训练数据带入网页噪声、基准奖励猜测、RLHF 固化讨好倾向；更大的模型只改变失败位置而非失败频率。对 agent 重要的两类：过期数据与捏造细节，均可靠实时检索缓解。 原文
  • Agent 的网页搜索与深度研究如何接入 — 搜索处理少量来源的快问快答，深度研究处理需要数百页的复杂查询；Retell AI、Botpress、Credal 等已在生产使用。 原文
  • 搭一个实时调研公司的 AI SDR — 用 Firecrawl /search 抓新鲜信号、scrape 端点配 JSON schema 抽结构化公司情报、OpenAI 写文案、Python 串联；关键在于发送时才做调研而非读陈旧名单。 原文
  • 搭建金融研究 agent — 先抓取实时来源再把数据交给模型，把 LLM 从事实环节移出；问题根源是训练数据有截止而财务数据按季度更新，模型会自信给出「过期的错」而非典型幻觉。 原文
