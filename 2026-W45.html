Perplexity Blog · 2026-11-02 · 周末整块

How we halved DNS build delay and cut memory use by 85%

Cloudflare Blog · 2026-11-02 · 周末整块

Cloudflare 优化了 DNS Zone Builder，使其从每秒处理 250 个变化扩展到 700 个，某些区域已有 2000 万条记录并趋向数亿。关键是把记录级变化从区域级全量构建中分离，先前单记录构建比全构建快 150 倍，百万记录规模下快 4250 倍；通过证明何时可以只更新特定设置来消除不必要的重建。这是数据密集系统中增量更新的经典优化问题。

→ https://blog.cloudflare.com/dns-targeted-zone-builds/

Replacing our Postgres queue at 45 million polls a day

Composio · 2026-11-05 · 碎片时间

Composio 团队替换了 Postgres 队列系统，原表中活跃行数 99000 条，但死元组（包括 TOAST 数据）达 8.72 亿，造成索引扫描效率低下。解决方案是将调度决策从 Postgres 移到 Temporal workflows，由它管理定时器并批量分发轮询，Postgres 仅保存持久化状态。日均轮询 4500 万次。这是 agent 事件驱动系统中队列设计的真实案例。

Silent Instrument Errors Reorder Agent Leaderboards

作者只凭公开产物审计了 HAL 和 tau2-bench 两个 agent 排行榜，发现打分基础设施本身在静默出错：一个通用 agent 因为对话结束方式不触发评分，只有约一半 episode 被打分，其余被记为失败，按 benchmark 自己的规则补判后 13 分的差距就消失了。另外还查出成本列把嵌套模型调用重复计数、把 grader 写入的动作记成 agent 动作、以及用新评估器重判旧轨迹导致名次反转、模式检查误读文件让分数塌陷 59–82 分。结论是评测流水线（打分、日志、回放、版本）本身就是测量仪器的一部分，而且是无声失效。文末给出若干低成本检查项，如报告被打分比例、从根 span 汇总成本、标注每条动作的来源。

为什么值得读：直接针对 agent 评测可靠性：告诉你读任何 agent 排行榜时该怀疑什么、自己搭评测时该加哪些自检。

→ https://arxiv.org/abs/2611.04399

Hard Issue, Weak Model, or Bad Run? Rethinking Failure Prediction for Coding Agents

论文质疑「读部分轨迹预测这次运行会不会失败」这类 agent 失败预测器究竟学到了什么。在 SWE-bench Verified 公开轨迹上，一个完全不看轨迹、只看该 issue 对其他模型有多难的参考分就达到 0.92 AUROC，而轨迹预测器只有约 0.62；在同一 issue 内，知道是哪个模型比预测器更能预测失败。扣除难度与模型能力后，轨迹带来的增益在统计上等于零。进一步地，按 issue 切换模型在留出运行上没有收益，best-single 与 any-model oracle 的差距不超过随机波动；重复运行实验显示重试只能救「坏运行」，救不了超出模型能力的 issue。

为什么值得读：把「轨迹监控 + 中途切模型/重试」这套常见编排策略的收益证伪，直接影响你设计 agent 可靠性机制的优先级。

局限：结论基于 SWE-bench Verified 单次尝试的公开轨迹，重复运行部分只是小规模 pilot。

→ https://arxiv.org/abs/2611.08285

How Should Agents See Code? Rethinking Code Representations for Agentic Software Engineering

把「agent 怎么看代码仓库」当作一个设计变量，比较 AST、调用图、模块依赖、文档增强检索和混合五种仓库表示工作流与原始 shell/grep 基线，在故障定位、SWE-bench Pro、SWT-bench、SecBench 四类任务上评估 Claude Code + Haiku 4.5 的成功率、token 和延迟。结论是表示层主要在「定位是瓶颈」时有价值：LinuxFLBench 上 recall@10 从 0.717 升到 0.757–0.829，且 token 用量降 25–39%；而在 SWE-bench Pro 上解决率与基线持平（44.3–50.6% vs 49.0%），token 降 17–26%。所有工作流都会增加延迟。

为什么值得读：是关于上下文构造与 token 预算的受控对比，给出「什么时候值得给 agent 建仓库地图」的可操作判据。

局限：只在一个模型（Haiku 4.5）+ Claude Code 一种 harness 上验证。

→ https://arxiv.org/abs/2611.07286

The Last Mile to the Real World: Agent-Native Primitives as Reusable Building Blocks for Solving Real-World Tasks

提出 agent-native primitive：把一个资源（工具、环境、文档）和一个常驻 LLM 打包成可复用单元，由它在上下文中实际使用该资源并与其他 primitive 通信，而不是把「会用」这件事留给调用方。HEELO 框架按任务把这些 primitive 组装成图、用环境证据校验结果、针对失败修订相关 primitive 并在验证后入库。在同一 backbone 上，Terminal-Bench 4.0 解决率从 Codex 的 37.3% 提到 55.5%，ToolBench pass rate 从 55.8% 到 75.1%，GAIA-Text-103 从 45.6% 到 58.3%。

为什么值得读：是「harness 工程」这一层的系统性方案：如何把能力沉淀成可复用模块而不是每个 harness 重写一遍。

局限：涉及八大类 primitive 的庞大工程，跨 20+ benchmark 的结果难以判断各组件的实际贡献。

→ https://arxiv.org/abs/2611.07461

Evolver: Turning Agent Exploration into Evolving Capabilities

Evolver 把 agent 探索中产生的过程性知识固化为结构化的 Gene 资产，包含获取、检索与基于反馈的演化，不改模型参数，可挂在现有 harness 上做「经验条件化执行」。在 Claude Code 与 Codex 两种 harness、两种模型、四个 benchmark（Terminal-Bench 2.1、SWE-bench Multilingual、SWE-rebench、GAIA）上评估。320 对配对执行中成功率从 83.13% 升到 87.50%，记录的任务执行 token 消耗下降 24.24%；在两种条件下都成功的 265 对中 token 仍降 17.57%，说明即使成功率不变效率也有提升。

为什么值得读：给出「经验/技能库如何跨 harness 复用并同时降低 token 成本」的可迁移机制与配对实验设计。

局限：320 对是作者挑选的诊断子集，不是全量 benchmark 结果。

→ https://arxiv.org/abs/2611.07595

Dittany: Contribution-Guided Repair Framework for MAS Applications

针对 LLM 多 agent 系统「产出了有用中间结果但任务要求未满足」的执行，提出 Dittany：从任务需求与方法规格推导预期贡献和验收条件，连成贡献图，运行时检查定位未满足条件并判断哪些中间结果仍可用，再做动作级修正或图级回滚。在 6 个 MAS 框架、30 个应用、9000 个任务上，失败检测精度 88.28%/召回 79.18%，任务准确率 84.76%，比最强恢复基线高 21.28 分。token 开销比原生高 17.92%，但比 Reflexion 低 24.19%、比迭代回滚低 13.05%。

为什么值得读：多 agent 编排中的运行时失败恢复机制，且把 token 成本与准确率放在同一张表上比较。

局限：贡献图与验收条件依赖对任务需求和方法规格的结构化描述，迁移到规格缺失的真实系统成本未知。

→ https://arxiv.org/abs/2610.42144

社区在聊什么

Agent 的编排骨架：模型路由、token 预算与「谁来干这一步」

这周最像方法论讨论的是成本分层。「A Jev that can ask Opus for help gives Opus accuracy at 4x lower cost」↑574↗ 把小模型 + 必要时升级求助做成了一条可复制的路由策略，拿到 Opus 级准确率却只花 4 倍更低的成本，评论区主要争的是「升级判定」本身要不要再花一次模型调用。YC Startup Library 的《Stop Wasting AI Tokens》↗ 和《The Right Model for Each Coding Task》↗ 是同一命题的实践版：按任务难度选模型、别让贵模型跑脏活。反面案例也有——「YC's Garry Tan uses AI agents so much, he spends up to $200K a year on tokens」↑111↗ 的评论比分数还多，争论点是个人年耗 20 万美元 token 到底是生产力拐点还是预算失控；「Anthropic's internal AI use, at retail prices, now exceeds its employee pay」↑352↗ 把同一个问题放大到公司规模。最值得翻的是「Ask HN: What's your current AI agentic setup?」↑556↗，687 条回复基本是一份社区自述的 harness 配置清单。

多 agent 协作与 agent 的「长期记忆」还没定型

多 agent 这周挨了一记实证耳光：「AI agent swarms in Minecraft fail to build civilization, drown in bureaucracy」↑180↗ 描述的是 agent 群体把算力耗在互相协调和流程上，这条被不少人当作「多 agent 协作当前上限」的注脚。上下文管理一侧，「The Components of Agent Memory」↑157↗ 试图把 agent 记忆拆成可讨论的组件，而「Memorilla: Latent Semantic Memory for LLMs」↑115↗ 热度不低但评论只有 13 条，说明方案尚未进入争论阶段。基础设施层有「Launch HN: Rivet (YC W23) – Scale and Orchestrate Agents on S3」↑120↗，把 agent 编排状态落在对象存储上；偏原生 agentic 的模型则是「LongCat-2.5: Native Multimodality for Agentic Tasks」↑86↗。另有一条冷水：「Basically no one is using AI agents for their DoorDash orders」↑178↗，评论远多于分数，争的是消费端 agent 到底有没有真实需求。

评测可信度：这周社区花了最多力气在「这个结果是真的吗」

「Astra can read and write weights to improve Qwen」↑2959↗ 是本周第一热，紧接着就出现了「The 'Astra can read and write weights to improve Qwen' post is misleading」↑1041↗ 和「LLMs are not superhuman at reading and writing neural network weights」↑151↗——一个宣称、两篇反驳，合计两千多条讨论，是观察「如何对 agent 成果做复核」的现成样本。相关的还有「GPT-6 Astra covertly underperforms on safety research」↑341↗，争的是模型在特定评测上是否存在策略性表现。纯评测方法论的是「MaxxBench – "Nice DeepSWE score. But is it true?"」↑276↗，直接质疑 SWE 类分数的可复现性；「Progress on provable inference for large language models」↑240，以及一个把「LLM 会说谎」做成玩法的「Show HN: Uncracked City」↑127↗。

把 agent 接进生产系统后的事故与权限面

这一组是系统设计和 AI 工程的交叉点，而且全是真实事故。「Claude Code sends your email address to websites」↑1594↗ 是本周争论密度最高的条目之一；「Claude Code's "Don't Ask Again" exposes passwords in 1,122 public GitHub files」↑332↗ 则把「工具调用授权一次就永久放行」的设计缺陷量化了。数据去向方面，「OpenAI seems to be silently re-enabling model training on Codex chats」↑531↗ 和「ChatGPT silently passes data between connectors」↑94↗ 共同指向同一件事：agent 的连接器就是新的数据出口。自建替代方案的讨论见「Revolut moves to self-hosted GLM」↑193↗。非 AI 的事故复盘素材同样够用：「Ubuntu still has not released patch for Linux 0day RCE in almost 3 weeks」↑626↗ 争的是发行版的补丁响应 SLA，「Gitbook Breached」↑165↗ 和「WorkOS reports security breach」↑81↗ 则是供应链身份层连环受击。

纯工程与学习工作流：数量不多但质量不错

系统设计一侧本周偏冷：「Show HN: Waymark – A workflow engine that compiles jobs instead of replaying」↑81↗ 讨论的是编译式工作流对 replay 式持久执行的取舍，正好能和上面的 agent 编排对照读；「Can GROUP BY still be optimized after all these years?」↑118↗ 是典型的查询引擎优化长文；「The Lisp curse, now coming to your ecosystem」↑239↗ 的 216 条评论几乎都在吵生态碎片化与工程规模化的关系。学习方向，最该看的是「So I guess everyone uses LLMs to think now」↑81↗，评论远超分数，争的正是「用 AI 思考」是否在替换掉主动回忆这类真正产生记忆的环节；「AI for scientific discovery: How researchers use Claude」↑101↗ 给了专业人士进入陌生领域的实际用法。输入源层面，「Show HN: HackerBooks」↑1867↗ 和「Show HN: HackerTV」↑488↗ 把 HN 的推荐沉淀成了书单与视频频道，可以直接当选材渠道用。
