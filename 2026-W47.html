How the Claude Code team thinks about verification

claude.dev Blog · 2026-11-16 · 周末整块

这是 Claude Code 团队在自家 claude.dev 博客发布的工程文章，作者 Addy Osmani，讨论编码 agent 如何用证据验证自己的工作。核心事实：团队约 90% 的代码由 Claude 编写和审阅，他们指出没有验证回路时只能同时运行一两个 Claude，有了验证回路可以并行几十到几百个。内部测试中，用独立评分器按 rubric 检查 Claude 产出，相比标准提示循环最多提升 10 个点的任务成功率，难题上收益最大。文章主张优先投资端到端测试、属性测试和差分测试，并说明团队如何保证验证器本身不出错。对他来说：如果把「给 agent 一个可自证的验证器」做进 harness，会直接决定并行 agent 的规模上限，而「独立 grader 对比自评」是可以照搬的评测模式。

Building the Agent Host Protocol for sessions that continue across devices

GitHub Engineering · 2026-11-17 · 周末整块

这是 GitHub 工程博客的文章，介绍 Agent Host Protocol（AHP）这一开放标准，目的是让 agent 会话跨设备延续。问题背景：GitHub Copilot 最初是 VS Code 扩展，扩展捆绑自己的 harness，导致 agent 生命周期绑定到单个窗口——关窗则 agent 消失，更新 VS Code 会重启并停掉所有 agent，连远程机器会得到一个锁定在特定 VS Code 版本的扩展宿主。同时 Copilot 独立应用和 iOS/Android 移动端各自与云端 agent 做不同的集成，每个集成只解决一个产品的问题。AHP 先在 VS Code 中构建、后被 GitHub 全线采用，使在 Copilot 里一处启动的 agent 会话可在另一处接着用。对他来说：这正面回答了「agent harness 该放在客户端还是独立宿主」的问题，会话状态与编辑器生命周期解耦是可迁移到自研 agent 的架构选择。

Context rot in AI agents: why long tasks lose accuracy and how to prevent it

Perplexity Blog · 2026-11-18 · 周末整块

这是 Perplexity 官方博客发布的一篇科普式指南，解释 agent 的「上下文腐化」（context rot）。它把 context rot 定义为长任务中随上下文填充而逐渐发生的准确率下降，上下文包含指令、历史消息、搜索结果、网页和文件文本，随任务推进不断累积。文中举例：任务是找两周内交货的供应商，中途上下文塞入几十个网站正文、几页搜索结果和已查清单后，agent 会开始把六周交货的供应商也算进去。它指出上下文窗口以 token 计量，腐化在步骤多的长任务里最容易发生，表现为偏离原始指令、漏细节、混淆相似信息。对他来说：这直接对应上下文管理和 token 预算的设计取舍，压缩与重置策略需要按任务长度而非固定阈值来定；但文中未给出具体缓解措施或量化数据。

8 ways to reduce the cost of evals

Arize AI · 2026-11-21 · 周末整块

这是 Arize AI 发布的博客，作者从一次线下活动上反复听到的「eval 太贵」抱怨出发，给出 8 条降低评测成本的方法。核心论点是 eval 成本主要来自默认设置——用最大的 judge 模型、把整条 trace 当输入、开着 reasoning、对每条 trace 都打分——而这些默认通常有更便宜的替代且精度不掉，所以成本是设计选择而非固定税。第一条建议是能用代码就用代码：判断标准是两个人在同一 rubric 下看同一 span 是否会给出不同结论，不会分歧的就用代码评测器，比如 schema 检查、格式检查和对照已知答案的比较。文中其余建议仅列出标题，材料未展开细节。对他来说：这提供了在评测预算受限时逐项拆解成本的结构，其中「两人是否会分歧」是一个可立刻套用的代码/LLM judge 分界线。

Design Once, Deploy at Scale: Building a Template-Driven ML Ecosystem

Engineering at Meta · 2026-11-18 · 周末整块

这是 Meta 工程博客的文章，介绍其模板驱动的 ML 生态，相关论文题为《Design Once, Deploy at Scale: Template-Driven ML Development for Large Model Ecosystems》。核心问题：Meta 广告排序系统每天处理数十亿请求、服务大量生产模型，瓶颈已从发明新技术变成把技术推广到每个适用的模型，逐个模型适配无法随规模扩展，碎片化会迅速累积。做法是把模型设计标准化为少量可复用、可组合的积木，把逐模型的迭代变成共享的系统问题。两年成效：每模型工程时间减少 92%，交付 5000 多个技术-模型组合，在同等服务容量下离线模型质量平均提升 0.63%，覆盖 70% 模型（按数量）带来 0.86% 的累计线上提升。对他来说：把「技术传播」当作独立系统问题并量化其收益，是规模化 ML 平台里少见的可迁移经验。

How LinkedIn Runs Compute: Self-Managed Kubernetes on 500,000+...

LinkedIn Engineering · 2026-11-19 · 周末整块

Does Your Agent Need to Know Its Budget? A Placebo-Controlled Experiment on LLM Coding Agents

通过安慰剂对照析因实验（5,835 runs）单独测量 token 预算执行与告知对编码 agent 的影响。强制预算上限使任务解决率下降 20 个百分点，但每个已解决任务的 token 用量降低约十二倍。告知 agent 预算没有任何帮助，唯一的“正效应”来自一句无关句子（安慰剂）。结论是预算治理应成为执行设计问题，而不是沟通问题。

为什么值得读：用随机对照实验直接回答 token 预算“执行还是告知”的问题，落在 token 预算与任务成本的核心痛点上。

局限：只在两个开源模型和两个程序修复基准上验证，未覆盖闭源 frontier 模型。

→ https://arxiv.org/abs/2611.21614

Revision-Consistent Code Context for Agents That Edit Their Environment

提出“混合 revision 代码上下文”问题：编辑型 agent 在查询时同时修改仓库，可能把不同 revision 的事实组合成不安全结果。方案是 agent 可见的 complete-revision 发布契约，要求同一响应内所有视图共享版本标识与发布边界，并在 Codetrip 中实现。对照实验中 live-source 组合在 150 次更新出现 2 次不安全响应，Codetrip 为 0；恢复试验 300/300 返回完整新上下文。Rename 探针中 Codetrip 混合上下文 0/30 vs 30/30。

为什么值得读：上下文管理在 agent 边编辑边查询时的一致性契约，是 agent 应用侧一个具体且可迁移的问题。

局限：只在 frozen Gin/Cobra 等仓库上验证，仓库范围和编辑场景有限。

→ https://arxiv.org/abs/2611.21616

Readie: Low-Latency Code Sandboxes for AI Agents

针对 AI 代理代码沙箱启动慢的问题，提出学习式启动快照，把单快照的紧凑与覆盖矛盾转化为一组快照的集合覆盖优化。在 15K 公共与 LLM 合成脚本上规划，Readie 在同一存储预算下把启动延迟降低 3–22 倍，端到端运行时间降低 1.3–3.3 倍。关键洞察是一组小快照可同时做到启动快和覆盖广。

为什么值得读：系统设计层面的基础设施优化，低延迟代码沙箱直接决定 agent 执行循环的可行性和成本。

局限：未详细说明跨语言、跨依赖生态的泛化边界。

→ https://arxiv.org/abs/2611.22171

Higher-Scoring Coding Models Did Not Get More Work Done

利用一次为期 19 天的出口管制导致用户被迫从 Claude Fable 5 切到低 11 分模型的事件，构造自然实验研究模型分数提升是否转化为真实生产力。对 297 名受影响用户与 8,908 名未切换用户的 PR 数据做双重差分，发现访问高分模型仅让 7 天合并率提升 1.4 个百分点，不显著。五次模型升级的合并率提升也均为负且不显著，说明 benchmark 分数提升没有转化为可测量的工作产出。

为什么值得读：用自然实验挑战基准分数与真实效能的关系，属于 agent 评测与可靠性中最需要的外部效度检验。

局限：只测量 PR 合并率和数量，未覆盖代码质量、长期维护成本等产出维度。

→ https://arxiv.org/abs/2611.23216

Idempotency Is Not Recovery: A Fault-Injection Study of Language-Model Agent Tool Actions

通过故障注入研究 LLM agent 工具调用中断后重试/幂等语义，区分“抑制重复副作用”和“恢复完成状态”。在 Windows/Linux 上 7,513 次试验中，完整运行时记录到 0/200 vs 117/200 次重复副作用；去掉 action ledger 后孤儿副作用 170/170。禁用 reconciliation 后 100/100 已知故障结果不明确；代价是吞吐约为 fail-open 的七分之一。

为什么值得读：工具调用幂等与恢复是 agent 可靠性的核心，故障注入数据清晰区分了“不重复”和“真正恢复”。

局限：在受控运行时和构造案例上验证，不完全代表生产环境中的故障复杂性。

→ https://arxiv.org/abs/2611.23353

SWE-CoWork: Benchmarking Coding Agents as Digital Employees in Organizations

在模拟软件组织中评估编码 agent：101 个任务、101 个真实仓库、11 种语言、12 个领域，包含 26 个有界知识同事。两个领先模型通过约 63% fail-to-pass 测试，但完整交付任务不足 8%。即使前置提供完整需求也只提升 F2P 测试约 16 个百分点，完整任务成功率不变；31% 自称完成的需求仍测试失败。

为什么值得读：多 agent 协作与组织级 agent 评测中，需求跟踪和跨同事信息获取是比局部实现更关键的瓶颈。

局限：模拟组织中的同事行为和知识边界是受控的，未必代表真实协作中的复杂度。

→ https://arxiv.org/abs/2611.20218
