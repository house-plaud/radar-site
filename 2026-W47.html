Introducing Perplexity’s Monitor API

Perplexity Blog · 2026-11-16 · AI 工程 · 周末整块

Perplexity 官方博客发布 Monitor API，面向需要持续跟踪网页变化的应用和 agent（如销售 agent 盯融资公告、编码 agent 盯 API breaking change、产品团队盯竞品定价页），解决目前靠定时搜索加自建去重代码、在数百主题和页面上难以维护的问题。Monitor 分两种模式：Web Monitor 用自然语言查询跑 Perplexity Search 抓全网和新闻的新进展，Page Monitor 跟踪最多 10 个指定页面，首跑存基线、后续返回文本 diff。Perplexity Decider 对每条结果做四道检查（相关性、来源可信度、新信息、时效性），Page 变更则判断是否对目标有意义，全部过阈值才推送，并带置信度分数，阈值和 goal 都可调且不必重建 monitor。调度支持 15 分钟、小时、日、周或自定义 cron，跨轮去重，更新通过签名 webhook 投递并对瞬时失败自动重试。官方自称在 60 个取自生产 Search API 查询的主题上各监控 8 小时，说自己的结果最新最全、很多结果其他 provider 完全没返回——这是官方软文，数据按宣传打折；对做 agent 编排的人，它提供了一个现成的「变更检测 + 事件触发」外部信号源，但准确率仍需自测。

How the Claude Code team thinks about verification

claude.dev Blog · 2026-11-16 · AI 工程 · 周末整块

Claude Code 团队（作者 Addy Osmani）在官方博客撰文，讲编码 agent 如何在规模化下用证据验证自己的产出，背景是团队约 90% 的代码由 Claude 编写与评审。核心论点是验证回路决定你能并行跑多少 agent：没有它只能同时跑一两个因为要自己全查，有了它能跑几十上百个；内部结构化文件生成测试中，另设 grader 按 rubric 打分比标准提示回路最多提升 10 分成功率，难题收益最大。文章推荐三类测试——端到端、属性、差分，并强调 E2E 最难被糊弄（单元测试超时 vs E2E 给出截图与具体损坏描述），可用 CDP、模拟器、API harness 让 agent 有手有眼。反模式也很具体：测试 flaky 会训练 agent 重跑而非修代码，测试慢会让 agent 少测、难以定位；并把失败用例沉淀成 hook 或 CLAUDE.md 规则来闭环。对做 agent harness 与可靠性的他，这是一份可直接照搬的验证层设计清单。

Context API extracts full context from any web page

Perplexity Blog · 2026-11-17 · AI 工程 · 周末整块

Perplexity 推出 Context API，解决 agent 读网页时的两难：搜索结果只给片段，直接抓页面又拿回满是导航、cookie 弹窗和广告的原始 HTML，而开发者还需要控制内容的新鲜度。接口一次最多读 10 个 URL，按请求顺序逐个返回，输出格式包括干净 Markdown、HTML、页面链接（绝对地址、去重、保持页内顺序）和 Snippets；Snippets 是按查询挑出页面上最相关的段落、受开发者设定的每页 token 上限约束，它选原文段落而不是生成摘要，模型拿到的是页面原话但更少的字。生成 Markdown 的做法是把页面切块、用模型给每块打「正文/模板」分，只保留正文块；每个成功结果还带标题、描述、语言、作者、发布日期和 Open Graph 标签等元数据。新鲜度默认先查两天内抓过的网页索引、没有才实时抓，max_age_seconds 设 0 可强制实时（价格、比分、突发新闻），cache_only 为 true 则永不触发实时请求，每个结果都记录来源是缓存还是实时抓取及抓取时间。对做 agent 上下文管理的人，这是一条能直接省 token 的取数通道。

Orchestrator: One API for reliable inference

Perplexity Blog · 2026-11-17 · AI 工程 · 周末整块

Why Thinking More Can Make an LLM Dumb

ByteByteGo · 2026-11-17 · AI 工程 · 周末整块

ByteByteGo 的这篇文章解释为什么推理模型想得更久反而可能答得更差，切入点是语言模型逐 token 生成时会同时参考原问题和已写出的内容，因此答案开头写下的东西会显著影响几句之后的计算。文中用「100 美元先涨 20% 再降 20%」的例子说明：写下中间结果 120 再算折扣就能稳定得到 96，而直接把两个 20% 当作相互抵消会得出错误答案，这正是 chain of thought 有用的一类情形；OpenAI 的 o1 等推理模型则是被专门训练成在给出最终答案前先生成中间推理。文章结构涵盖模型如何基于自己的输出继续推理、推理模型回复前发生了什么、额外时间的优势、如何教模型利用更多步骤、模型何时已经想够了，以及额外一步如何把正确答案变成错误答案。对他的意义：这直接关联 agent 里「推理预算该给多少」的取舍 —— 多步思考不是单调收益，harness 需要对简单任务设推理上限，而不是统一给最高推理档。材料是二手综述性质，文中引用的具体实验与数字在摘要范围内未给出，这一点不足。

Why large monorepos need code search, especially with AI coding agents

Sourcegraph · 2026-11-17 · AI 工程 · 碎片时间

Sourcegraph 官方博客论证大 monorepo 为什么仍然需要代码搜索，尤其在 AI coding agent 加入之后，针对的是「代码都放一个仓库了所以 grep 就够了」这个常见假设。论点一：本地的 grep、IDE 找引用、git status 都要扫本机文件，规模一大就崩——Canva 2022 年说自己的 monorepo 约 50 万个文件、全新 clone 后一次 git status 要等约 10 秒。论点二：常用解法 sparse checkout 让本地工具重新变快，但每个开发者和每个 agent 只看得到仓库的一个切片，一次「看起来完整」的搜索可能漏掉根本没 checkout 的调用方，monorepo 的承诺被悄悄收回。Sourcegraph 的方案是把索引放在服务端、覆盖整个仓库，搜索、代码导航和代码理解都跑在这份共享索引上，对每个工程师和每个 agent 都一致。另一点是 grep 只匹配文本不匹配语义，搜 validate 会把定义、调用点、注释、日志和重名函数全捞出来，精确导航才能区分定义、引用和恰好同名的字符串。这是厂商自述，结论按宣传折价。
