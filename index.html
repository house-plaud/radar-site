Agent tool selection: The tool your agent almost called

Arize AI · 2026-10-19 · 周末整块

When Code Becomes an LLM Call: An Empirical Study of Call-Site Contracts in Agentic Systems

对 40 个开源 agent 系统（13.4 MLOC、四种语言）里的 496 个 LLM 调用点做了实证研究，追踪每个模型输出流向哪里，并把「代码本应保证什么」的期望契约与实际实现的前置条件、提示约束、后置检查逐一对照。结果：48% 的 LLM 输出直接进入控制流或执行，其中 73% 从不经过人；82% 的调用点前后都有检查，但 63% 的期望约束未被满足，只有 5.3% 的调用点满足完整契约。十种复现模式解释了 99% 的缺口，38 个运行时可触发的机制都能被一处小补丁堵住。

为什么值得读：把「agent 把一部分程序逻辑外包给 LLM 调用」当作可测量的工程契约问题，给出 harness 代码该在调用点前后加什么检查的具体清单。

→ https://arxiv.org/abs/2610.24545

SWE-Residual: Evaluating Starting-State Robustness of Coding Agents

提出 SWE-Residual：现有 SWE benchmark 都从干净状态起步，但现实中 agent 常常接手别人已声称完成、实则仍失败的工作。作者从 DeepSWE 和 Terminal-Bench 的 111 个任务构造 198 个「残留状态」，只给原始请求和被污染的仓库/机器状态，不给前任轨迹。五个前沿 agent 成功率最多掉 53.5 个百分点，DeepSWE 上排名甚至反转；失败模式是「接受偏见」——把继承来的工作当成任务定义，58.9–88.2% 的失败运行提交时失败的测试与起始时完全相同。

为什么值得读：揭示了一个被所有 benchmark 忽略的可靠性维度：多 agent 接力和人机交接场景下，起始状态本身就是攻击面。

→ https://arxiv.org/abs/2610.25899

Pack Light, CarryOn: Building Object-Oriented Context for Long-Horizon Agents

CarryOn 提出面向对象的上下文运行时：长程 agent 不再靠压缩历史或重建进度摘要来续写，而是把进展组织成可复用的「任务对象」（continuation carrier）＋补充执行上下文＋最近交互的尾部。关键机制是在历史被折叠retire后跨折叠维护 carrier 记录，只对受影响的记录依据绑定证据和环境检查做增量修订，而非每次重建全量表示。在 OSWorld 2.0 和 BrowseComp-Plus 上分别提升 5.8% 和 7.0%，同时 token 用量最多降 51.9%。

为什么值得读：直接针对长程 agent 的上下文管理与 token 预算：给出「围绕进展而非历史组织上下文」的可操作设计。

局限：只在两个 benchmark 上验证，carrier 的抽取质量对任务类型的依赖程度未充分讨论。

→ https://arxiv.org/abs/2610.18784

Where Should a Stuck Agent Spend Its Next Tokens? Causal Attribution of Inference-Time Resources

把推理期扩展从「加 token」重新拆成三类资源——算力、信息、反馈，用 Banzhaf 归因框架在固定失败状态和修复协议下做受控析因实验，测每类资源的边际贡献。覆盖 6 个模型、MBPP+/HumanEval+ 的 194 个函数级失败和 SWE-bench Verified 的 126 个仓库级失败。结论：任务相关的规格说明最有用，公开测试反馈增益很小，检索到的代码几乎无用；而四个前沿模型中有三个在 95–100% 的情况下选反馈，收益反而低于均匀随机选资源。

为什么值得读：回答「卡住的 agent 下一步该把预算花在哪」，并量化了模型自选资源与实际有效资源之间的系统性错配。

局限：只覆盖代码修复场景，资源三分法是作者定义的，是否能迁移到其他 agent 任务未验证。

→ https://arxiv.org/abs/2610.28834

Can LLMs Improve Their Own Harness? A Controlled Study on ARC-AGI-3

在 ARC-AGI-3 上做受控实验，问前沿模型能否自己写出并迭代改进自己的 harness（感知、记忆、工具、恢复、推理分配的调度程序）。每个模型从固定 bootstrap 出发构建完整 harness，在 5 个开发游戏上运行并做两轮全代码库修订，再在 20 个从未参与适配的游戏上评估。27 条演化谱系的表现从零到接近天花板都有，但两轮修订在留出集上平均只带来 2.80 分提升（95% 区间 [-1.44, 7.35]），开发集增益显著高估了留出集增益，降低推理成本往往以任务性能为代价。

为什么值得读：当下大量论文在卖 harness 自演化，这篇是少有的受控、带留出集、结论偏负面的对照研究，值得当解药读。

局限：只有两轮修订预算、单一 benchmark，不能排除更长演化周期下结论改变。

→ https://arxiv.org/abs/2610.30499

Stale Instruction Files Override the Code in Coding Agents: A One-Sentence Fix

构造 40 个 Python 项目，让 CLAUDE.md / AGENTS.md 里的约定与仓库里既有代码的实际写法冲突（如文件要求 print、代码用 logging），让 Claude Code 和 Codex CLI 各加一个功能，共 320 次运行。无干预时 90.1% 的选择跟随过期的指令文件，Claude Code 在 80 次中 79 次明确指出了冲突却仍然照做，Codex CLI 有 20 次反过来改写既有代码，其中 17 次把项目自己的测试跑挂。在用户级指令文件里加一句「以既有代码优先」，跟随代码的比例升到 91.4%，测试通过率从 89.4% 回到 100%。

为什么值得读：指出指令文件以「指令」身份进入上下文、代码以「工具输出」身份进入，优先级天然不对等——这是 harness 层上下文组织的一个具体可修 bug。

局限：人为构造的冲突场景，仓库规模小，真实项目中冲突的频率与形态未测。

→ https://arxiv.org/abs/2610.30571

社区在聊什么

harness 才是 agent 的身体：编排、会话与多 agent 协作

这周社区最集中的一个争论是"模型之外的那层壳到底算不算工程"。《Harness Engineering 101: The LLM is the brain, the harness is the body》↗↑132把 harness 提到了与模型同级的位置，评论区分成两派：一派认为 harness 只是临时补丁、模型变强就会被吃掉，另一派拿实测反驳——《Five Qwen3.8-27B models match Fable 5 Using GVS5H Harness》↗↑138正是"编排补模型"的直接证据。具体手法层面，《Tmux and Claude Code: Sessions, Send-Keys, and the Ceiling》↗↑172讨论了用 tmux send-keys 驱动 agent 会话的天花板在哪，标题里的"Ceiling"本身就是争论焦点：终端多路复用能撑住几个并行 agent？《Show HN: Corgi, a helpful {agent, terminal} multiplexer》↗↑131和《Show HN: Omnara – Open-source alternative to Claude Managed Agents》↗↑112是两个不同的答案，后者直指托管式 agent 的黑箱问题。多 agent 协作上最热的是《Claude Duet》↗↑565，评论比分数还接近 1:1，说明争议极大；运行时隔离则由《OpenShell – A safe, private runtime for fleets of autonomous AI agents》↗↑499承接。另有一条偏架构的讨论值得单独看：《Hybrid Reasoning Agents: LLM agents that think in latent space, act through text》↗↑520，争的是"思考"要不要落回 token。CLI 侧则有《OpenAI CLI》 —— 更正：《OpenAI CLI》↗↑243。

评测与可靠性：别让模型给自己打分

《Using LLM for confidence scoring is a bad idea》↗↑226这周基本定调了一个共识方向：把模型自报的置信度接进控制流是危险的，这对任何做 agent 可靠性门控的人都是直接可用的结论。评测本身也在吵：《SlopCodeBench 10/2026 – Opus 5.5, Astra wins overall, xhigh considered harmful》↗↑305里"xhigh considered harmful"是争论核心——更高的推理档位反而掉分；《RuneScape Bench: MMOs for Agents》↗↑249则在推一类长时程、带环境状态的新评测形态。可靠性的坏消息来自几个侧面：《How Far Will AI Assistants Go for a Refund They Can't Get?》↗↑107是典型的 agent 越界行为观察，评论数超过分数；《Qwen3-Coder writes less secure code when told it's for a US persona》↗↑242揭示 prompt 里一句无关身份描述就能改变产出质量，这对任何做上下文模板的人都是警示。正向路径有两条：《LLMs are making formal software verification feasible at a much larger scale》↗↑457主张用形式化验证兜住模型输出，《Using Claude to reduce the attack surface of code》↗↑136是同一思路的小规模实践；训练侧则有《Turning Database Grading into RL Rewards: Post-Training Agents with ThinkingBox》↗，把可执行的数据库评分当奖励信号，属于"评测即训练"的做法。另有《Advanced coding in low-resource programming languages》↗↑109讨论评测覆盖不到的语言。

token 预算、代理层与"推理比训练重要"

成本这条线这周有一个很清晰的主张：《Why Inference Matters 12x More Than Training》↗（配套的 Paper Club 视频见↗）把重心压在推理侧，口号是推理重要性 12 倍于训练。落到工程上，《If you don't run your own LLM proxy, how do you know whats going on?》↗↑303是本周最该读的一条：争论点是自建代理层到底是必要的可观测性基建，还是又一层会坏的中间件——支持方的论据基本都是"不自己代理就拿不到 token 账单、重试和超时的真实分布"。单位成本被摆上台面的是《DeepSeek search and fetch – $0.75 per 1000 successful requests》↗↑606，"successful requests"计价口径引发了大量关于失败重试谁买单的讨论；推理栈本身则由本周最高热度的《DeepInfer: High-performance inference framework for DeepSeek models》↗↑2347和《DeepSeek V4.1 Flash 1017 (Max)》↗↑190占据。

agent 的输入端正在变脏：关门、投毒与反爬

这组讨论对"上下文管理"有直接影响——agent 读到的东西正在被人为操纵。《WhatsApp's help pages hid LLM instructions: dont recommend a regulator》↗↑743是本周争论最激烈的一条，帮助页里藏给 LLM 的指令，等于把 prompt injection 做成了常规 SEO 手段；《Publish fake stats, get cited in LLMs》↗↑369是同一现象的另一半——伪造数据反向污染模型引用。供给侧则在关门：《Websites are closing their doors to AI agents》↗↑159评论几乎与分数持平，争的是 agent 流量该不该被当作爬虫对待；更极端的表态是《I built a programming language that LLMs can't use》↗↑282。做 agent 工具调用的人应该把这几条当成"外部数据不可信"的默认前提来读。

系统设计：一次欧洲级宕机、一次提前泄露的禁令期

和 AI 无关但价值最高的几条都在可靠性与流程上。《Google Cloud outage affects almost all banking and other operations in Europe》↗↑406是本周最大的事故素材，讨论集中在单云依赖与金融系统的爆炸半径。漏洞披露流程连出两起人为事故：《Tell HN: I unknowingly broke the PHP RCE embargo. I am sorry.》↗↑734是一篇罕见的第一人称复盘，《Several Linux kernel vulnerabilities accidentally posted to public mailing list》↗↑252是同类问题的第二次。依赖链的爆炸半径分析可看《Node2Shell evolves to HTTP2Shell, blast radius affects many HTTP libs and apps》↗↑298与《Evolving Threat: http2shell is an RCE in Node, Python, and more》↗↑182，协调响应侧则是《Patch the Planet: global response coordination as agents uncover vulnerabilities》↗↑266。基础设施设计上，《Let's Encrypt is adding two additional remote perspectives for domain validation》↗↑267是教科书级的多视角一致性验证案例；迁移经验见《Roku developer repositories moved from GitHub to GitLab》↗↑283，配置可复现性的争论见《NixOS is making me less afraid》↗↑199，漏洞面板则有《CVE Tracker》↗↑217和跨固件栈的《One parser, two bugs, many routers》↗↑103。
