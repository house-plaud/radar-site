When Agents Fail: Model or Harness--Who's to Blame?

提出用五个互补指标评估 harness 与模型的「交互」而非各自孤立表现：有效完成率（VCR）、Model-Harness Fit、Cross-Model Fit、Interaction Residuals、以及含失败尝试在内的 Token Load。实验覆盖 4 个通用 harness（OpenCode、Codex CLI、Pi CLI、DeepAgents）× 4 个模型加 2 个原生组合，6 个 benchmark（上下文管理、工具使用、长程规划、多模态、交付物交接），共 111 组设置、52,168 条 trajectory。结论是 harness 排名随模型和 benchmark 而变，任务分数相近的配对执行画像可能完全不同，任务正确率和有效完成率也常指向不同的最佳配对。

为什么值得读：把「harness 选型」变成一个可量化的多维决策，而不是看一个 leaderboard 分数——正是 harness 与编排这一块最缺的评测方法论。

局限：所有结论都是特定模型/harness 版本的快照，版本一变排名就可能重排。

→ https://arxiv.org/abs/2610.32483

The Hidden Costs of Forgetting: A Study of Trajectory Deletion in Software Engineering Agents

系统探索 42 种在线 trajectory 削减配置（删除的范围、粒度、比例、时机），在 SWE-bench Verified 上用两个 SOTA agent 跑了 9,400 次。发现删掉旧 turn 中高达 100% 的 reasoning 文本仍能保持整体效果，但必须延迟删除——立即删会显著掉点；agent 会通过重新抓取被删内容来补偿，导致 turn 数和输入输出 token 反而上升。成本上，按扁平计价 42 组中有 26 组省钱，按带 prompt caching 的计价则 0 组省钱，因为削减打断了低价计费的缓存前缀。

为什么值得读：直接回答「上下文削减到底省不省钱」——结论是只数 token 会误导你，必须在真实缓存定价下算账。

局限：只在 SWE-bench Verified 和两个 agent 上验证，成本结论强依赖具体厂商的缓存计价模型。

→ https://arxiv.org/abs/2610.35496

Tool-Calling LLM Agents Under Realistic MCP Faults: Scale Does Not Purchase Fault Tolerance

构建 MCP-Injector——一个协议层的故障注入中间件，可在 MCP 工具调用路径上以可控持久性（永久/瞬时/间歇）和可复现调度注入故障，故障分布标定自 1,774 个开源 MCP 仓库、57,240 条 issue 与 PR 的真实事故统计。1,350 组实验横跨两种 backbone 规模（20B/120B）、三种 agent stack（自建 plan-and-execute、OpenAI Agents SDK、LangChain）。故障下任务完成分从 8.08 跌到 3.23，且 120B 并不比 20B 更抗故障（resilience-ratio p=0.96）；不同 agent stack 的故障吸收能力差异明显。

为什么值得读：工具会坏是生产环境的常态，而现有 benchmark 默认工具永远正常；这篇说明容错来自框架级错误处理而非模型能力。

局限：backbone 只取了 gpt-oss 20B/120B 两档，「规模无用」的结论外推到其他模型族需谨慎。

→ https://arxiv.org/abs/2610.32555

Knowing When to Stop: The Evidence-Action Gap in Coding Agents

提出 ImpasseBench：在本可解的修复任务中注入 12 种真实环境阻塞，并在每条 trajectory 上标注「证据已足够说明只有外部帮助才能推进」的那一步，从而把合理努力、过度坚持和过早交接区分开。8 个前沿模型、19,371 条 trajectory 显示，几乎所有需要求助的 run 都收集到了充分证据，却仍有三分之一耗尽预算，所有被检出的不安全请求都发生在该步之后。给 agent 一个 escalation 工具后，预算耗尽率从 34.0% 降到 6.7%；对忽略工具的模型，外部 monitor 让环境恢复后的任务成功率接近三倍。但升级出的工单常只说明阻塞、不说明自身进度与验证状态。

为什么值得读：「什么时候该停下来找人」是长程 agent 可靠性里被忽略的一环，这篇把它变成可测量的指标并给出了低成本的 harness 补丁。

局限：阻塞是人工注入的，真实环境里「证据何时足够」的那一步未必这么清晰可标注。

→ https://arxiv.org/abs/2610.31895

Free to Look, Free to Reason: Simple LLM Harnesses Outdiagnose Hand-Crafted Root Cause Analysis Agents

在 RCAtlas（来自 8 个公开数据集的 90 个已验证微服务故障案例）上，把三种完全不规定模型调用步骤的简单 harness（单次调用读证据包、SQL agent、Codex 编码 agent）与五个已发表的 LLM RCA agent 及统计/因果方法做对照，跨 6 个模型、3 档 reasoning effort。简单 harness 的 PR@1 达 65–77%，已发表 agent 只有 16–53%，非 LLM 方法 6–39%，且在所有同时跑过两类方法的模型上都成立。已发表 agent 把十分之一到全部的模型调用写死在程序里，case study 显示这些预设流程恰恰跳过了决定性证据。

为什么值得读：对「手工编排 SOP／角色分工 agent」的一次强力证伪，且给出了成本/时间上的 Pareto 比较——编排越多不等于越好。

局限：领域是微服务根因分析、仅 90 个案例，是否迁移到长程编码类任务未验证。

→ https://arxiv.org/abs/2610.35767

What Effort Level Should I Choose? On the Economics of Reasoning Effort in LLM Agents

把 reasoning effort 档位当作「信任品」来研究：用户在选档时无法知道多花的算力是否必要。作者在 4 个 benchmark（含单次推理与长程 agent 任务）上对专有与开源模型做反事实测量，发现高 effort 虽能提升总体准确率，却会做坏一部分低 effort 原本解出的任务；在所有档位都能解的简单任务上，最高档成本最高可达最低档的 42 倍；高 effort 还会改变行为模式（更多自我验证、更多搜索而非直接求解）。一个简单策略——从最低档起、仅在验证失败后升档——在所有模型和 benchmark 上匹配或超过固定最高档，且对多数专有模型更便宜。

为什么值得读：给 effort/预算这个旋钮一个可操作的默认策略，正对「token 预算与任务成本」这条。

局限：各厂商对 effort 档位的定义不统一，跨模型的成本倍数可比性有限。

→ https://arxiv.org/abs/2610.34491

学习方法与"用 AI 进入陌生领域"
