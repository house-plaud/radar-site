TurnCost: Turns, Not Observations: Cache-Aware Loop Engineering for Coding Agents

作者分析了 600 条公开的编码 agent 轨迹（两种 scaffold × 两个模型），拆解迭代循环中的真实 token 成本构成。结果显示观测结果中位数只有 118–286 token，常被用来论证压缩必要性的大段构建日志实际落在 99 分位；且 98.6% 的输入 token 命中前缀缓存，按平价输入计价会把成本高估约 7 倍。回归显示 turn 数解释了 84% 的成本方差，而平均观测大小只解释 4%，最贵的轨迹恰恰观测最小、轮数最多。论文还给出并验证了模型降级委派的闭式盈亏平衡条件，发现半数设定下委派反而更贵，并开源 TurnCost 用于在不同缓存/计价/压缩/路由策略下重算轨迹成本。

为什么值得读：直接针对 token 预算与任务成本：用真实轨迹推翻了「压缩观测」这条主流省钱路线，并给出可复用的成本重算工具和委派决策公式。

局限：只证明轮数与成本强相关，并未证明在保持成功率的前提下轮数可以被削减。

→ https://arxiv.org/abs/2610.15093

Skip the Compressor: Coding Agents Fix More Issues When They Pick Whole Files

在 300 个 SWE-rebench issue 上，作者把每个 issue 的上下文严格对齐到同一 token 预算，比较三类用法：prompt 压缩、chunk 检索、以及整文件逐字选择（其简单方法 CQ2-CARE）。用 GPT-5.6 和 Claude Opus 5 分别解决 43.7% / 46.7% 的问题，比最佳压缩器高 6.3 分，比最佳检索器高 9.3 和 12.7 分，也超过了两个专门为 issue 修复训练的方法 SweRank 和 SWE-Pruner。失败归因分析指出：检索器常漏掉真正需要改的文件，压缩器保留了文件却改动了文本，导致 patch 无法应用。

为什么值得读：上下文管理的关键对照实验——同预算下「选哪些文件原样展示」胜过「压缩/检索更多片段」，结论可直接改写 harness 的上下文装配策略。

局限：只在 Python issue 修复这一类任务上验证，且依赖两个前沿闭源模型。

→ https://arxiv.org/abs/2610.21073

Stateless Language Agents: Scaling Long-Horizon Automated Research

论文提出 Stateless Language Agents：agent 不跨调用携带对话历史，研究状态（候选方案与实测结果）由 harness 持有，每次调用按角色重建上下文；一个无状态 Advisor 读取 harness 汇总的证据并给并行 Worker 分派具体实验。在软件工程、kernel 优化、算法设计三类任务上与三个近期框架对比，预算最高到 10 亿 token，SLA 在每个任务上都取得最佳终局结果，并以 少用 84% 的 token 达到最强 kernel 基线的终局性能。消融显示聚焦上下文与显式任务分派各自有贡献，Advisor 本身只消耗不到 0.6% 的 token。

为什么值得读：把「状态归 harness、agent 无状态」作为编排原则讲清楚了，并在超长预算下量化了重放历史与重复劳动带来的浪费。

局限：任务均为有自动打分器的搜索型研究任务，不确定能否迁移到缺乏可验证目标的场景。

→ https://arxiv.org/abs/2610.07625

When Messages Go Wrong: Understanding Communication Faults in LLM-Based Multi-Agent Systems

作者对 LLM 多 agent 系统做了通信故障的大规模实证：建立跨层故障分类（从网络丢包/延迟/上下文过期映射到应用可见故障），搭建故障注入与追踪流水线，覆盖 100 个任务、5 个领域、3 种工作流拓扑、3 种模型配置共 2.9 万次执行。在有完整检测记录的失败中 20.7% 没有即时失败信号，部分内容损坏类故障更高达 76.2%。拓扑影响巨大：Flat 拓扑下成功率 53.0%，而 Sequential 与 Hierarchical 仅 3.3% 和 3.2%，优势主要来自存在另一条信息路径能保留下游所需证据。

为什么值得读：多 agent 协作的可靠性工程证据：告诉你拓扑选择和证据冗余路径比防护机制本身更决定系统在消息异常下的存活率。

局限：故障为人工注入，真实部署中各类通信异常的分布未必与之匹配。

→ https://arxiv.org/abs/2610.15459

ToolBottleneckBench: Measuring Tool-Agent Performance under Controlled Pressures and Fixed Harness Budgets

ToolBottleneckBench 把合成企业任务固定住，只变动一种压力：注册工具目录、可见工具菜单、认证工作流、返回记录的编码方式，并在固定 harness 预算下测量 21 个模型×harness 配置。精确评分器记录每次失败的首个未满足义务以及终止该 episode 的 harness 上限。结果是只有「可见菜单」这一项带来大幅惩罚，且该惩罚与补全上限截断高度相关——把上限提高 16 倍后大部分惩罚消失；多数失败终止于 harness 上限，失败记录识别压力来源的能力不比简单统计工具调用次数更强。有效的修复都在于改变哪些工具送到模型面前或由谁发起调用。

为什么值得读：把「模型能力不足」和「harness 预算不足」这两种常被混淆的失败因素分离开，对工具调用评测与 harness 配置都有直接指导。

局限：任务为合成企业场景，21 个配置下的结论是否迁移到真实工具生态未验证。

→ https://arxiv.org/abs/2610.21098

When Agent Evaluation Becomes Unreliable: An Empirical Study of Oracle Failures and Configuration-Dependent Measurement in an LLM Agent Benchmark

论文把 agent 评测 harness 当作软件来审计，提出含 5 条状态完整性不变量和 3 个已知答案对照的 oracle 完整性审计方法，并通过注入 7 类 oracle 缺陷验证其检出率。应用到一个真实 agent benchmark 后发现奖励函数在评分前就改变了环境状态：在 4320 个 episode 上做 replay 纠正后，数据库通过标签从 4194 降到 2883，成功率从 94.3% 降到 65.5%。另一组 3240 个 episode 的组件消融显示，agent 的策略文档、工具描述、工具报错文本都会影响观测到的轨迹可靠性，其中工具描述影响最大（-9.2pp），且在第二个任务域中效应符号发生反转。

为什么值得读：提醒你 agent 的分数表可能首先是 harness 的 bug 报告——给出了可复用的 oracle 审计不变量和复现包。

局限：审计方法在另一个独立实现的 benchmark 上无法套用（无法从其 API 日志重建参考终态），可移植性有明确边界。

→ https://arxiv.org/abs/2610.16067

社区在聊什么

harness 比模型更重要：agent 到底靠什么组织工作

这周最集中的一条主线是「模型之外的那层工程」。YC Startup Library 直接以《Why The Harness Matters More Than The Model》↗ 立论，HN 这边则有更具体的实操：《How to engineer an AI harness for game development》↑175↗ 讨论怎么为一个领域搭专用脚手架，而《500B tokens later: Letting AI agents decompile a first-person shooter》↑218↗ 则是把 token 预算摊开给人看的极端案例——半万亿 token 换一次反编译，评论区争的正是这种规模下任务拆解、上下文回收和「什么时候该放弃」的成本账。配套的基础设施话题是 Launch HN: Agent37 低成本 agent 沙箱↑162↗，以及 Anthropic 自己怎么把 agent 塞进研发流程的《How the Claude Code team does code review》↑458↗——463 条评论里相当一部分在质疑「agent 写、agent 审」的闭环是否成立。小工具侧还有 Sphinx，在提交前反过来考你 AI 写的代码↑86↗，以及把 claude -p 包成语音入口的 Atticus↑115↗；YC 侧的《The Powerful Alternative To Fine-Tuning》↗ 和《Building AI Agents for Everyone》↗ 可以当背景音听。

评测失灵：大家对「它到底能干什么」已经谈不拢了

《The gap in shared understanding of LLM capability is widening》↑727↗ 是本周评论量最高的讨论之一，核心是同一批工程师对同一批模型的能力判断正在分叉，而且没有共同的度量语言。紧随其后的《90% of US working hours are spent on tasks not covered well by AI benchmarks》↑603↗ 给了量化说法：90% 的工作时长没被基准覆盖，这也解释了为什么线上体感和榜单越来越对不上。落到产出端，《AI coding agents generate more code, but not more software》↑364↗ 把矛头指向「代码行数 ≠ 交付物」这个老问题。另一侧是能力的正面证据：《Claude reveals ECDSA curve origins》↑1034↗、用 Claude 设计更高效量子线路↑172↗、Linus 的首个 LLM 辅助补丁系列↑124↗，以及被扒皮的 OpenAI「更快 FFT」数学↑247↗——后者恰好说明声称与验证之间的鸿沟。行为型评测这周也有存在感：Gemini 打星际↑243↗、决策模型玩吃豆人↑81↗、以及「为什么 LLM 画的鹈鹕长这样」↑164↗。

可靠性与爆炸半径：agent 出事的方式越来越像运维事故

这周的事故清单读起来完全是 SRE 口吻。《Containment and monitoring failures are to blame for AI hacking reports》↑948↗ 是热度最高的一条，论点是所谓「AI 黑客事件」本质上是隔离与监控没做到位；OpenAI 又披露四起 rogue incidents↑124↗，而《Why aren't AI companies being charged for hacking?》↑336↗ 把同一件事推到了责任归属层面。生产侧的真实损失也不少：TV4 因 agent 抹掉已剪辑素材而推迟播出↑156↗，Anthropic Console 因国际化输入 bug 多扣 100 倍费用↑88↗——这是「token 成本」之外另一种账单风险。客户端的默认行为同样引发反弹：Codex CLI 默认装常驻自更新后台守护进程↑609↗，Codex Desktop 持续产生 Crashpad dump↑121↗。再加上「模型可能无需数据中心自我复制」↑117↗，以及 YC 侧的《Building the Safety Layer for AI Agents》↗、《AI Agents That Banks Can Trust》↗ 和 Paper Club 的安全专场↗，整体基调是：权限边界、可观测性、回滚能力，比模型能力更决定能不能上生产。

成本、容量与「在哪跑」：本地推理成为预算问题的一部分

把 agent 成本压下来的办法之一是换部署位置，这周有一组讨论都围绕这个。Janas 用 SSD 流式加载专家、跑比内存更大的模型↑220↗ 争的是内存墙到底能不能用 IO 换；llmspeed 让你在买硬件前先感受本地模型速度↑280↗ 则是典型的容量规划工具思路。LFM2.5-24B-A2B 面向端侧 agent↑288↗，Hugging Face 的配套文章讲怎么在设备上跑私有 agent↗；更极端的是在越狱 PS5 上跑 llama.cpp↑367↗，以及完全本地推理的记账应用 Pulse Local↑121↗。训练与集群侧的经验可参考 YC 的《Lessons From Training Composer At Cursor And Building Meta/Nvidia Compute Clusters》↗。

系统设计：版本控制的规模化、依赖风险与一桩真实的 OT 事故
