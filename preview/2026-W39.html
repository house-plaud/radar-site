Brownfield Agentic Engineering

Addy Osmani · 2026-09-14 · 周末整块

Addy Osmani 发文讨论在遗留代码库中使用 agent 的工程问题。brownfield 系统的核心困难在于代码库不再是系统实际行为的完整描述，机构知识、临时方案和其他团队的依赖存在于版本库之外。直接在这类代码库上部署无监督 agent 容易导致代码「有效但设计不当、测试脆弱」，需要将改动优化为安全且成本低的操作。与 AI 前的现代化工作一样，必须采用分段式改动配合强力测试来保证不破坏既有行为。这对想用 agent 快速迭代的团队意味着需要先梳理隐性约束、建立可靠的验证机制，否则 agent 输出可能看起来可用但潜伏系统设计风险。

→ https://addyosmani.com/blog/brownfield-agentic-engineering/

Jev vs LLM-as-a-Judge

OpenRouter · 2026-09-21 · 碎片时间

OpenRouter 博客对比 Jev 决策模型与 LLM-as-a-judge 模式用于 agent 输出评分。LLM judge 输出文本判决，Jev 输出类型化问题的概率；在闭合标准且证据包含在请求中时，准确率相当，但 Jev 成本低 1/5、延迟低 1/10，概率校准更好；开放标准和需要全文阅读时，LLM judge 更贴近专家评分。建议根据标准类型选择：Jev 适合闭合标准、证据自含（答案可溯源、符合政策）的场景。这对大规模 agent 评测的成本和速度优化有直接价值。

→ https://openrouter.ai/blog/tutorials/jev-vs-llm-as-a-judge/

Jev introduces a new shape of LLM - System One, aka Decision Models

Simon Willison · 2026-09-21 · 碎片时间

Simon Willison 介绍 TypeSafe AI 推出的 Jev，一类新的 LLM 变体被称为「System One 模型」（Willison 认为「decision models」更好）。Jev 接受文本输入但输出浮点数对应分类、是非题、评分和置信度，而非生成文本，仅按输入 token 计费，输出免费，定价为每百万 token $0.042，比 GPT-5 Nano ($0.05/M) 还便宜。支持 yes/no 题（Bernoulli 分布）、评分题、开放分类，常用于对数据或文本做结构化判断。对 agent 评测和成本控制有直接影响，特别是在需要大量决策评分的场景。

→ https://simonwillison.net/2026/Sep/21/jev/

We just shipped support for the ugliest part of HTTP: Vary

Cloudflare Blog · 2026-09-22 · 碎片时间

Cloudflare 博客讨论 HTTP Vary 响应头的缓存支持实现。Vary 被称为「HTTP 最丑陋未改进的部分」，用于告诉缓存哪些请求字段可能影响响应，但不说明哪些差异真正重要，导致相似请求可能扩展成数千条低复用缓存条目。Cloudflare 在 Cache Rules 中新增 Vary 支持，允许源声明可能变化的头，缓存层决定如何处理——可归一化已知协商头、精确通过关键值差异、或在变化太大时绕过缓存。与 AI 无直接关系但代表缓存策略复杂性的工程实践，对 agent 系统的多模型响应变异管理有参考意义。

论文

100 篇候选中选出 6 篇（预算 6 篇）。arXiv 无投票机制，取舍由语义判断，不是按热度。

Grow the Harness, Not the Context: From Strategy-Free Scaffolds to Reusable Specialist Agents

提出 Growing Harness：从一个「无策略」脚手架出发，用任务失败反馈把反复出现的控制逻辑固化成可执行代码，而把 LLM 调用只留给任务相关的语义推理。方法上用函数级执行轨迹把失败定位到有界代码面，批量修复一窗口失败，并用「成功优先」的held-out 门控回滚有害改动。在 BrowseComp-Plus 和 WebArena-Verified 上、4B 到 120B 三种部署模型中，六个设置里五个取得最高平均成功率，相比 Tool-Calling agent 减少 76–92% 的 LLM 调用；4B 模型下 WebArena 成功率仍保持 44.7%，而 Tool-Calling 跌到 6.7%。

为什么值得读：直接回答「控制逻辑该放在 context 里还是放进 harness 代码里」，并给出成本与小模型可用性的量化答案。

→ https://arxiv.org/abs/2609.26760

CliffCompaction: Cost-Efficient Compaction for Long-Horizon Coding Agents

CliffCompaction 是面向长周期 coding agent 的上下文自动压缩方法，核心约束是只做截断/丢弃、绝不改写，且从不压缩已压缩内容（每轮只作用于原始内容，丢弃旧压缩输出），以避免上下文漂移累积。在受限上下文下成本 最多降低 50%，同时在 Terminal-Bench 上保持或提升表现。压缩带来的单轮节省改善了 test-time scaling 的性价比曲线；在 KernelBench 上跨百万 token 会话持续迭代，400 步达到 3.58× CUDA 加速。作者开源了与 scaffold 无关的 API-proxy 实现，可直接接 Claude Code、Codex。

为什么值得读：context 压缩是长任务 agent 的第一性成本问题，这篇给出了可直接套用的工程规则与开源实现。

→ https://arxiv.org/abs/2609.26779

RRSI: Regularized Recursive Self-Improvement of Agent Harnesses

指出 harness 自动演化（RSI）存在对训练任务的过拟合：in-distribution 大涨但换 benchmark 就消失。RRSI 在提议侧加时间退火的编辑预算并鼓励未探索方向，在选择侧加 critic（筛掉 benchmark 特异的提议）和 pruner（剔除过小、过贵、失效的改动）。在覆盖编码、agent workspace、工程设计的八个 benchmark 上，演化所用 split 最多涨 14.1 分，而 OOD 上 最多提升 4.7 分，同时产出的 harness 少用 30% policy token。

为什么值得读：如果你在做 harness 自动优化，这篇点出了最容易踩的坑（演化即刷榜）并给了具体的正则化手段。

→ https://arxiv.org/abs/2609.24972

FIRE: Failure-Informed Runtime Engineering for Reliable Language-Model Agents

研究「运行时策略」：在 harness 层面对历史失败前置状态注入定向自然语言指令和动作拒绝，不改权重也不改用户 prompt。在完整 87 题 Terminal-Bench 2.1 上每题两次尝试，三档 GPT-5.6 的 pass^2 全部提升，最强档 重复成功率提升 9.2 个百分点，而 best-of-two 只变 1.2 分——说明策略主要把「能解出来」变成「稳定解出来」。五臂随机对照显示真实策略 61%，无策略 39%，时间匹配的假策略 36%，通用「再验证一下」类提示 39–43%，排除了安慰剂效应。

为什么值得读：把「可靠性」和「能力」拆开度量，并用对照实验证明 harness 层干预本身有效，是 agent 可靠性工程的干货。

局限：只在 Terminal-Bench 单一套件、单一模型家族上验证，策略需针对已观察失败人工/半自动构造。

→ https://arxiv.org/abs/2609.26048

Where Does Exactly-Once Live? Model, Harness, and Tool-Contract Effects on Duplicate Side Effects in LLM Agents

问「exactly-once 语义该由模型、harness 还是工具契约来保证」。作者建了 LIMBO 沙箱（六个服务、真实契约、十二种在服务边界注入的故障，含延迟提交、重投、部分批次），跑了 25,930 个 episode，覆盖九个模型、三种生产 harness、两种契约变体。结论是分场景的：当能立刻回读确认时模型说了算（前沿模型重复写只有 0.5%，模型解释了 53% 方差）；当无法回读（请求仍在途或传输重投）时前沿模型也会在 56%/74% 的 episode 重复，此时契约解释 81% 方差——给每个写操作提供幂等 key 使重复率 从 28% 降到 4%，而 harness 几乎不起作用。

为什么值得读：工具调用侧最实际的可靠性问题，给出了「责任该落在哪一层」的可操作结论而非泛泛建议。

→ https://arxiv.org/abs/2609.29095

Just-in-Time Memory: Learning to Curate Task-Adaptive Memory for LLM Agents

指出现有 agent 记忆系统都在「写入时」固化经验（反思、workflow、skill），必须在未知未来查询前就决定留什么，且要有长程 credit assignment。JitMem 反过来保留原始轨迹、把 curation 推迟到读取时：给定检索到的轨迹和当前任务，由一个 curator 合成紧凑的任务自适应 payload，因而可直接用当次任务成功率训练。在 ALFWorld、WebShop、τ²-bench 上分别比最强基线 提升 16.2 个百分点、16.3 和 3.9；未训练的 curator 已经能打平或超过基线，说明收益主要来自读时自适应而非训练。

为什么值得读：对「agent 记忆到底该在写入还是读取时压缩」给出了清晰的机制性答案，直接关系到上下文与 token 预算设计。

局限：三个 benchmark 都偏玩具化的交互环境，未在真实长周期工程任务上验证。

→ https://arxiv.org/abs/2609.27334
